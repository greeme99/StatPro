# StatPro 오픈소스 도입 및 공급망 품질 게이트

## 1. 목적

StatPro는 공개 통계 근거와 오픈소스 구현을 구분한다. 공개 수식·표준은 독립
통계 구현의 근거가 될 수 있지만, 특정 패키지를 제품 런타임에 포함하는 결정은
별도의 라이선스·공급망·검증 심사를 통과해야 한다.

이 게이트는 법률 자문이나 취약점 스캐너를 대체하지 않는다. 저장소에서 확인할
수 있는 의존성 등록, SPDX 라이선스, 잠금파일 일치, SBOM 최신성을 fail-closed로
검사하는 기술적 기준선이다.

## 2. 소유 파일

| 파일 | 책임 |
|---|---|
| `compliance/oss-policy.json` | 허용 SPDX 라이선스와 직접 의존성의 목적·경계 |
| `web/package-lock.json` | 배포 및 개발 npm 전이 의존성의 정확한 버전·무결성 |
| `compliance/statpro-sbom.cdx.json` | 결정론적으로 생성된 CycloneDX 1.5 컴포넌트 목록 |
| `tools/oss_gate.py` | 정책, manifest/lock 일치, 전이 라이선스, SBOM 최신성 검사 |

Python 선택 의존성은 현재 `pyproject.toml`의 범위 요구사항만 존재하고 잠금파일이
없다. SBOM은 이를 `declared-not-locked`로 명시한다. 릴리스 패키지 재현성을
주장하려면 플랫폼별 Python 잠금 또는 배포 산출물에서 추출한 별도 SBOM이
추가로 필요하다.

## 3. 필수 절차

새 의존성을 추가하거나 버전을 변경할 때 다음 순서를 따른다.

1. 사용 목적과 코어/어댑터/UI/테스트 경계를 정한다.
2. 동일 기능을 내부 코드나 기존 의존성으로 해결할 수 있는지 확인한다.
3. `compliance/oss-policy.json`에 직접 의존성을 등록한다.
4. npm이면 `package.json`과 `package-lock.json`을 함께 갱신한다.
5. `python tools/oss_gate.py --write`로 SBOM을 다시 생성한다.
6. `python tools/oss_gate.py --check`와 전체 관련 테스트를 실행한다.
7. 통계 결과에 영향을 주는 패키지는 공개 기준 벡터와 독립 비교를 추가한다.

미등록 직접 의존성, manifest/lock 불일치, 라이선스 누락, 허용 목록 밖 SPDX
식별자, 오래된 SBOM은 모두 실패한다. 복합 라이선스 식의 모든 선택지를 허용
목록과 비교하므로 `OR` 식도 임의로 안전하다고 간주하지 않는다.

## 4. 허용 범위와 도입 경계

- D3·Recharts는 표시 계층만 소유하며 통계량이나 관리한계를 계산하지 않는다.
- React Router는 URL/작업 흐름 상태만 소유하고 분석 상태의 진실 원천이 아니다.
- 테스트 패키지는 운영 통계 결과의 출처로 승격하지 않는다.
- 외부 패키지의 결과를 기준값으로 사용할 때는 버전, 실행 환경, 입력, 허용오차,
  재현 한계를 Evidence 문서에 기록한다.
- Copyleft, 소스 공개 의무, 네트워크 제공 의무 또는 상업 배포 제약이 의심되는
  라이선스는 자동 승인하지 않고 별도 법무 검토 대상으로 둔다.

## 5. 버전 변경 정책

- 정확 버전이 잠긴 npm 전이 그래프만 빌드에 사용한다(`npm ci`).
- 직접 의존성의 주 버전 변경은 API·UI 회귀와 SBOM 검토를 요구한다.
- 통계 시각화 라이브러리 변경은 접근성 표 대체물, 누락값, 한계선 포함 범위,
  내보내기 결과를 다시 검증한다.
- 보안 수정은 기능 변경과 분리할 수 있지만, 잠금파일과 SBOM은 같은 변경에
  포함한다.

## 6. 현재 결론

현재 npm 잠금 그래프의 선언 라이선스는 정책 허용 목록 안에 있다. Python 선택
의존성은 직접 등록됐으나 정확한 배포 그래프가 잠기지 않았으므로 부분 검증
상태다.

### ECharts 6.1.0 비교 스파이크

ECharts는 제품 코드가 아닌 `web/benchmarks/chart-engines/`에만 설치했다. 정책의
`benchmark-only` 경계는 `web/src`에서 ECharts를 가져오면 게이트를 실패시킨다.
ECharts의 잠금 그래프가 추가한 `tslib`의 SPDX `0BSD`도 명시적으로 검토해 허용
목록에 등록했다.
공식 문서에 따르면 ECharts는 Canvas와 SVG 렌더러를 제공하며, 1천 개를 넘는 큰
데이터에서는 Canvas 사용을 권장한다. 접근성 설명은 `AriaComponent`를 명시적으로
등록해야 하며 기본값은 꺼져 있다. StatPro의 접근성 표 대체물은 엔진과 무관하게
계속 유지해야 한다.

- 공식 렌더러 지침: https://echarts.apache.org/handbook/en/best-practices/canvas-vs-svg/
- 공식 접근성 지침: https://echarts.apache.org/handbook/en/best-practices/aria/
- 공식 모듈 가져오기 지침: https://echarts.apache.org/handbook/en/basics/import/
- 공식 SVG SSR 지침: https://echarts.apache.org/handbook/en/how-to/cross-platform/server/

동일 탭에서 1개 선, 애니메이션 없음, 1200×600 SVG DOM 생성 시간을 비교했다.
이는 단일 개발 환경의 방향성 측정이며 상호작용 지연과 최대 메모리는 측정하지
않았다. 원본은 `docs/evidence/chart-engine-browser-benchmark.json`, 격리 번들
측정은 `docs/evidence/chart-engine-bundle-benchmark.json`에 보존한다.

| 점 수 | Recharts 중앙값 | ECharts SVG 중앙값 | Recharts SVG 문자 | ECharts SVG 문자 |
|---:|---:|---:|---:|---:|
| 1,000 | 73.2 ms | 6.7 ms | 43,074 | 20,633 |
| 10,000 | 968.9 ms | 14.4 ms | 176,672 | 53,472 |

격리 번들의 gzip JavaScript는 Recharts 159,033바이트, ECharts SVG
168,526바이트였다. ECharts가 큰 SVG 선 그래프에서 유의미하게 빠르지만 현재
관리도는 통상 작은 부분군이며 기존 Recharts 접근성·내보내기 회귀가 충분히
구축되어 있다. 따라서 제품 런타임은 현 상태를 유지한다. 실제 분석 Run에
1,000개 초과 점을 표시해야 하는 요구가 확정되면 Canvas 기반 지연 로딩
어댑터를 별도 수직 증분으로 도입하고, 키보드 탐색·표 대체물·PNG/SVG 내보내기와
피크 메모리를 브라우저에서 재검증한다.
